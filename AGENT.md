## What PEAK is

PEAK is an adaptive learning app for kids built around a mountain climbing metaphor. A learner types a skill, PEAK generates a personalized climbing route from base camp to summit, and each waypoint on the route is a concrete challenge. Progress up the mountain is visible. Struggle is visible. Recovery is visible.

The core idea is: **adaptive learning visualized as terrain.**

PEAK 2.0 is not a from-scratch rewrite. It is a structured evolution of the hackathon prototype toward a robust, portfolio-quality product. The learning loop already works. The job now is to make the foundation solid, the visuals intentional, and the adaptation real.

- **Phaser, Pixi, Babylon** — no game engines
- **CSS-in-JS** — no styled-components, no emotion, Tailwind only
- **Redux, Zustand, Jotai** — use React state + context unless complexity demands otherwise (ask first)

### Rule: no new dependencies without a reason
Before adding a package, ask: can this be done with what's already installed? If yes, don't add it. If no, add it and leave a comment in the relevant file explaining why it was added.

## Domain model (the data shapes everything)

This is the most important section. The 2.0 architecture moves from a flat array to a graph. Understand this before touching any data layer.

### Mountain
Represents one learning journey (one skill). A learner can have multiple mountains active.

```ts
type Mountain = {
  id: string
  skill: string
  estimatedHours: number
  createdAt: string
  completedAt: string | null
  waypoints: Waypoint[]
  edges: RouteEdge[]
  attempts: Attempt[]
  adaptationEvents: AdaptationEvent[]
}
```

### Waypoint
A single challenge/concept on the route.

```ts
type Waypoint = {
  id: string
  mountainId: string
  title: string
  summary: string
  challenge: {
    type: 'text' | 'photo'
    prompt: string
  }
  difficulty: 1 | 2 | 3 | 4 | 5
  x: number        // 0-1 normalized, generated by layout engine (NOT AI)
  y: number        // 0-1 normalized, lower = higher on mountain
  isDetour: boolean  // true if this was generated as an adaptive support node
  mainPathId: string | null  // if detour, which waypoint does this rejoin
  status: 'locked' | 'active' | 'completed'
}
```

### RouteEdge
The visible path segment between two waypoints.

```ts
type RouteEdge = {
  id: string
  mountainId: string
  fromId: string
  toId: string
  isBranch: boolean  // true if this is a detour branch, not the main path
  pathData: string   // SVG path string (d attribute), pre-computed by layout engine
}
```

### Attempt
Records a submission and its outcome.

```ts
type Attempt = {
  id: string
  waypointId: string
  mountainId: string
  submission: string | { imageBase64: string }
  feedback: string
  passed: boolean
  confidenceScore: number  // 1-5, AI-estimated from submission quality
  createdAt: string
}
```

### AdaptationEvent
Records why and how the route changed.

```ts
type AdaptationEvent = {
  id: string
  mountainId: string
  waypointId: string  // the waypoint that triggered the event
  reason: string      // human-readable: "3 low-confidence attempts"
  detourWaypointIds: string[]
  createdAt: string
}
```

### Key rule: AI generates content. Code generates geometry.
AI (Claude) generates: `title`, `summary`, `challenge`, `difficulty`.
Deterministic code generates: `x`, `y`, `pathData`, layout positions.
Never ask AI for coordinates. Layout is a code concern.

## Architecture: separation of concerns

### State split
There are two distinct state domains. Keep them separate. Never mix them.

**Learning state** — what the learner has done, is doing, and needs to do.
- Which mountains exist
- Which waypoints are locked/active/completed
- All attempts and their outcomes
- Adaptation events
- Owned by: React state (or context), persisted to localStorage for now

**Scene state** — what the camera and visual world are doing.
- Camera position and zoom level
- Which waypoints are animating
- Trail draw progress
- Character position
- Atmospheric effect toggles
- Owned by: the scene layer (framer-motion + SVG refs), NOT React state
- Rule: React must not re-render the scene to change visual state. The scene layer animates itself. React only provides the data.

### Layer stack (bottom to top)
```
1. Canvas layer     — atmosphere, fog, particles, weather (passive, always running)
2. SVG layer        — mountain paths, route edges, trail glow, waypoints
3. Character layer  — climber sprite, positioned along route
4. React UI layer   — challenge cards, panels, navigation, overlays
```

Each layer only talks to the layer directly above or below it. React UI never directly touches the canvas. The SVG layer doesn't know about challenge state.

## The layout engine

The layout engine is a pure function that takes a list of waypoints (with content but no coordinates) and returns them with `x`, `y` assigned and `edges` with `pathData` computed.

It must:
- Start waypoints near the base (y close to 1.0) and end at the summit (y close to 0.1)
- Move generally upward (each waypoint has lower y than the previous on the main path)
- Introduce horizontal variety (zig-zag, switchback) so the route looks natural
- Avoid waypoint overlap (minimum distance constraint)
- Support branching (detour waypoints attach to a main path waypoint and rejoin later)
- Be deterministic given the same seed (same skill produces the same geometry)
- Return SVG path strings ready to use as `d` attributes

The layout engine lives in `web/src/lib/layout.ts`. It is pure TypeScript with no React, no framer-motion, no side effects.

## Milestones

Work through these in order. Never start a milestone until the previous one is demonstrably working. Ask Mohammed to confirm before advancing.

### Milestone 1: Foundation cleanup
**Goal:** Remove hackathon assumptions, establish the domain model, separate learning state from scene state. The app must still work at the end.
- Replace flat `Waypoint[]` with the full domain model above
- Move all learning state into a dedicated context (`MountainContext`)
- Move scene state out of React and into scene layer refs
- Remove any hardcoded paths or demo-only assumptions from production code
- Update Zod schema in `ai/validate.ts` to match new domain model
- All existing functionality still works after this milestone

### Milestone 2: Procedural visual route generation
**Goal:** Replace the fixed SVG path with the layout engine. Route geometry is generated, stored, and replayed.
- Build `web/src/lib/layout.ts` with the layout engine
- Generate route coordinates from waypoint list (no AI, pure code)
- Render stored geometry (edges with `pathData`) instead of hardcoded paths
- Animate the route being drawn from base camp to summit on first load
- Waypoint challenge flow is preserved

### Milestone 3: Adaptive rerouting
**Goal:** When a learner struggles, the route branches with a support detour.
- Track `Attempt[]` per waypoint in `MountainContext`
- Detect struggle trigger: 3 attempts with `confidenceScore <= 2`
- Call `POST /api/generate-detour` with current waypoint context
- Insert detour waypoints into the mountain graph
- Run layout engine on the new nodes to generate branch geometry
- Render branch visually (different color, branching from current position)
- Branch rejoins main path or continues to summit

### Milestone 4: Multiple mountains
**Goal:** Learner can have multiple active learning journeys.
- Mountain selection/overview screen
- Multiple mountains in state, each independently tracked
- Switching between mountains without losing progress
- Mountain completion state (summit reached)
- Persist all mountains to localStorage (structured, not ad hoc)

### Milestone 4.5: Dev tools
**Goal:** A hidden `/dev` route for testing without corrupting product state.
- Complete/uncomplete any waypoint
- Jump active waypoint forward or backward
- Reset a waypoint, a route, or all local state
- Replay animations (route reveal, trail fill, waypoint complete, detour, summit)
- Force an adaptive detour trigger from any waypoint
- Load canned test routes for animation QA
- All controls gated behind `import.meta.env.DEV` or `VITE_ENABLE_DEV_TOOLS=true`
- Zero dev tool logic in production code paths

### Milestone 5: Animation polish and character layer
**Goal:** The mountain feels like one continuous living place.
- Climber character travels along the route, pauses at waypoints
- Smooth camera motion (base → active waypoint → branch → summit)
- Canvas atmosphere layer (fog, snow particles, subtle lighting)
- No visible React rerender resets during scene transitions
- Summit sequence (celebration, mountain completed)

### Milestone 6: XP and progression
**Goal:** Meaningful rewards that reinforce learning, not generic gamification.
- XP for: completing waypoints, recovering after struggle, finishing a mountain, maintaining consistency
- XP does not replace challenge completion — it supplements it
- No leaderboards, no vanity metrics, no streaks that punish
- Simple, visible progress indicator tied to real learning behavior

## Coding standards

### File naming
- Components: `PascalCase.tsx`
- Utilities, hooks, lib: `camelCase.ts`
- Context files: `MountainContext.tsx`, `SceneContext.tsx`
- Prompt files: `routeGeneration.ts`, `submissionEval.ts`

### Component size
- If a component exceeds 150 lines, it needs to be split
- One component, one responsibility
- If you're scrolling to find a specific piece of logic, it belongs in a separate file

### Comments
- Leave a comment above every function that isn't self-explanatory
- Leave a comment above every piece of non-obvious logic
- Leave a comment explaining why, not what (the code says what)
- Example: `// Difficulty 1-2 uses smaller step sizes to keep early waypoints close together`
### TypeScript
- No `any`. Ever. If you don't know the type, find out.
- Prefer explicit return types on all functions
- Export types from `shared/schema.ts`, import them everywhere else

### Error handling
- All AI calls wrapped in try/catch with specific error messages
- All Zod validations use the safe parse variant in retry loops
- User-facing error states should be friendly and not expose internals
- Console errors are acceptable during dev but must be cleaned before milestone close

### State rules
- Learning state lives in `MountainContext`
- Scene state lives in the scene layer (refs, not useState)
- Never store derived state (anything computable from existing state)
- Never put scene animation state in React

## AI integration rules

### Route generation
- One Claude call per route generation
- Parse and validate with Zod on every response
- Retry once with the repair prompt if validation fails
- Cap at 2 total attempts, then surface an error
- Never use AI-generated coordinates for visual layout

### Submission evaluation
- Evaluate `passed` generously — kids need encouragement
- `confidenceScore` (1-5) is used for adaptation logic, not shown to users
- Photo submissions use Claude vision — pass image as base64 with the challenge context

### Detour generation
- Triggered by code, not by user action
- AI generates new waypoint content (title, summary, challenge, difficulty)
- Layout engine assigns coordinates
- Detour waypoints are marked `isDetour: true` in the model

### Prompt files
All prompts live in `ai/prompts/`. Each has its own file. No inline prompt strings anywhere else in the codebase. If a prompt changes, it changes in one place.
